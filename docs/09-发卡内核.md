# 09 · 发卡内核

> 卡密只是钥匙，真正的事在它之后。

## 1. 一句话

市面上的发卡系统解决的是「收钱 + 吐卡密」：买家付款，从库里取一条预先录好的卡密给他，
交易结束。

但很多虚拟商品的卡密不是商品本身，**只是一把钥匙**。买家拿到之后，
真正要发生的事才刚开始——要为他分配资源、跑一段可能几十分钟的流程、
等一个外部结果、确认成不成、失败了要退回库存并退款。

这个模块管的是**卡密之后那一段**。

## 2. 为什么不能用显而易见的做法

显而易见的做法是：卡密表加个「已用」字段，用了就标记。

它在长耗时履约面前会漏掉四种状态：

| 状态 | 显而易见的做法怎么处理 |
|---|---|
| 已扣款，履约进行中 | 没有这个状态。要么算已用，要么算没用，两边都不对 |
| 履约失败，钱该退 | 没有退款路径 |
| 部分完成（多次卡用了 1 次） | 「已用」是布尔的，表达不了 |
| 余额不够，要补差价 | 完全没有 |

而这四种全是**真金白银**——处理错一个方向就是白送，另一个方向就是纠纷。

## 3. 踩过的坑

### 3.1 支付回调会重发，没有幂等就是白送

外部支付通道的异步通知**一定会重发**。网络抖一下、你的服务慢一点，
同一笔订单的通知会来两次、三次。

没有幂等的话，一次网络抖动 = 白送一张卡。

做法是按订单号幂等：同一个订单号再次调用，**返回上次那张卡，不新发**。

```
issueCard({ orderId, ... })
  订单号已存在 → 返回原来那张，标记 reissued
  不存在       → 发新卡
```

> 这条对任何"外部系统会重试的接口"都成立。
> **幂等键要用外部系统的标识（订单号），不是自己生成的。**
> 自己生成的每次都不一样，等于没有。

### 3.2 先占坑再花钱

取号这一步要调外部付费接口。顺序有讲究：

```
❌  调外部接口拿到号  →  写进数据库
✅  先插一条占位记录  →  被唯一索引挡下就直接拒绝，压根不调外部接口
    →  调用成功再回填  →  失败就删掉占位
```

错误的顺序会出现**钱扣了、号拿不到**：外部调用成功了，
写数据库时被并发约束挡下，这次调用的钱就白花了。

正确顺序里，数据库先说"可以"才去花钱。

### 3.3 多次卡是共用钱包，必须扣掉已花的

一张可用多次的卡，第一版的预算计算只看面额。

后果是：面额 ¥3.99 的三次卡，三次各按 ¥3.99 的预算去买，
实际成本 ¥8.6，卖 ¥3.99 —— **一单亏 ¥4.6**。

正确的预算是：

```
可用预算 = 面额 + 已确认的补款 − 已经花掉的
```

三项缺一不可。少了「已花掉的」是上面那种亏法；
少了「已补的款」是反过来——买家补过一次之后想再买贵的，差额从头再算一遍，多收他的钱。

而且这个计算**必须和取号时那道闸用同一套输入**，
否则会出现「弹窗说补 X 元，补完取号又说不够」。

### 3.4 卡的有效期只能对新卡生效

给卡加有效期这条规则上线时，如果对存量卡一起生效，
**上线那一刻库里的卡会死掉一大批**——其中有些是几小时前刚发到买家手上的。

等于我们自己制造一波"描述不符"退款。

做法是：规则上线前的老卡（没有起算时间的那些）**永不过期**，
只对新发的卡计时。

> 一般规矩：**给存量数据加约束时，默认只对新数据生效。**
> 要对存量生效必须是明确决定，并且先数一下会影响多少条。

### 3.5 不变量交给数据库，不交给自觉

两条硬不变量：

- 一张卡只能成功收码一次
- 一张卡同时只能有一个进行中的履约

代码里当然有检查，但**兜底靠数据库唯一索引**。
应用层的检查负责给友好报错，索引负责保证它真的不会发生。

以后每加一条新的调用路径都可能绕过应用层检查，但绕不过索引。

### 3.6 后台不该看到完整卡密

对账只需要后四位。把完整卡密发到浏览器里，
等于给管理页面凭空增加一块泄漏面——而它换不来任何东西。

退款处理也按后四位定位；**撞号时报错，不猜**。

### 3.7 卡密字符集要去掉容易认错的字符

`0/O`、`1/I/L` 手抄必错。字符集去掉它们之后剩 31 个可打印字符，
分组显示（`XXXX-XXXX-XXXX`）进一步降低出错率。

这不是细节：买家抄错一次就是一次客服。

## 4. 代码在哪

`server/cards.js` —— `CardStore` 类，48 个方法，7 张表，**零本地依赖**。
用的是运行时内置的 SQLite，没有引入任何第三方数据库驱动。

| 组 | 方法 |
|---|---|
| 发卡 | `issueCard`（面额 / 服务锁 / 多码 / 前缀 / **按订单号幂等**）、`voidCard`、`verifyCard`、`getCard` |
| 会话 | `createSession` / `resolveSession` / `dropSessions` |
| 履约状态机 | `reserve` → `fulfill` → `consume` / `forceConsume` / `cancel` / `releaseReservation` / `settleAfterCode` |
| 补差价 | `claimTopup` / `confirmTopup` / `markTopupPaid` / `rejectTopup` / `consumeTopup` / `listPendingTopups` |
| 退款 | `listRefundRequests` / `resolveRefund` |
| 账目 | `ledgerSummary`、`listMoneyAtRisk`（**已收款但未完成履约**）、`spentCny`、`codesUsed` |
| 防刷 | `recordAttempt` / `ipLockRemainingMs` / `countMailboxesByIp` |
| 清扫 | `sweep` |

预算计算在 `server/pricing.js` 的 `checkRegionAllowed`——
它返回的不只是"行/不行"，还有原因（`no_price` / `no_card` / `need_topup` / 已补款放行），
调用方按原因分支，不是按布尔值。

**限速有个坑值得单独说**：挂在反向代理后面时，所有请求的来源地址都是回环地址。
如果不识别这种情况，"同一 IP 失败 5 次锁 30 分钟"会把**全站买家一起锁掉**——
刚付完钱的人第一次输入就看到"试得太多了"。

处理方式是：检测到这种情况时**主动降级掉买家侧那条限速**，
但保留管理口令那条（那条锁住是对的，只有卖家一个人用）。
宁可放弃一条限速，也不能把付过钱的买家挡在门外。
