# 01 · 五阶段链路

> 从一封信到一次完成的操作，中间没有人。

## 1. 一句话

一封信到达邮箱之后，机器要自己走完这些：建账号、读邮箱验证码、处理手机验证、
完成一次 OAuth 登录、驱动一个桌面客户端产生一次真实操作，
最后**自己判断这一切到底成没成**。

全程没有人在电脑前。中途任何一步出错，也没人喊停。

## 2. 为什么不能用显而易见的做法

显而易见的做法是：**写成一条直线**。上一步做完做下一步，出错就重试。

它在这里行不通，有三个原因，每个都不是"多写点代码"能解决的：

### 资源不可再生

链路消耗的东西**用一次就没了**：一个邀请名额、一个只能被邀请一次的账号。
普通自动化失败了重跑一次就是，这里失败一次就是**永久少一份**。

所以链路不能设计成"错了再来"，得设计成"每一步都尽量别把不可逆的东西烧掉"。

### 有个总时限

账号从建成到可用之间有个窗口，窗口关了后面全白做。所以链路带一个**总预算**，
从"信到达"那一刻开始掐表，每一步都打耗时。

这也意味着**不能无限重试**。重试三次和总共花多久，是同一个预算里的两种花法。

### 中间状态必须活着

第 2 步登录成功之后拿到的那个会话，第 4 步还要用。

直觉做法是每一步用完就关浏览器省内存——实际后果是第 4 步开一个全新浏览器、零会话，
OAuth 要从头再走一遍（约 100 秒），而客户端那边的本地回调只活约 60 秒。
**"省内存"换来"回调必然超时"。**

所以链路里有一个 2.5 阶段，它什么都不做，就是**不关那个浏览器**。

## 3. 踩过的坑

### 3.1 阶段划分本身是从事故里长出来的

```
1    等信            读邮箱。每分钟心跳汇报信箱里实际有什么
2    建账号          打开链接 → 邮箱验证码 → 资料页
2.5  保住登录态      ← 这一阶段唯一的作用就是不关浏览器
3    起客户端        抓 OAuth 链接，确认本地回调监听已就绪
4    走 OAuth        密码屏 / 资料页 / 手机验证三个分支都在这
5    确认成立        挑战-应答，见 02
```

阶段 3 里"**确认本地回调监听已就绪**"是单独一步，不是顺带做的。
先起客户端再去点登录、和点完登录再看客户端起没起，差别是：
后者会把 OAuth 回调打到一个还没开始监听的端口上，而这个失败**没有任何报错**——
浏览器那边显示登录成功，客户端这边什么也没发生。

### 3.2 别让账号停在"要密码才能登"的状态

链路里遇到"创建密码"屏时，第一版实现是**照着填一个密码**。

看起来没问题，实际上它把账号变成了「要密码才能登」，而我们没有地方存那个密码。
后果是**下一次重跑直接卡死在登录页**，账号彻底进不去——
一次可恢复的失败被升级成了永久损失。

改法是：遇到设密码相关的屏，**一律选一次性验证码那条路**，
让账号始终停在无密码状态。这样重跑和首次跑走的是同一条路径。

> 更一般的规矩：**自动化流程里每一个"顺手做了"的动作，都要问一句
> "它会不会让下一次重跑变得更难"。** 让状态可重入，比让单次跑得漂亮重要。

### 3.3 点击超时不能按"正常情况"设

有一屏的按钮**找得到、但点不动**——那一屏有过渡动画，自动化框架的可操作性检查
（可见/可用/静止）会一直等它稳定下来。5 秒的超时在那里必然失败。

改法两条：超时放宽，并且加一层"卡住就强制点击"的兜底。
兜底必须用框架的强制点击，不是直接调元素的 click 方法——
后者派发的是不可信事件，很多页面根本不认。

### 3.4 状态清不干净会让排查白费一整轮

客户端的本地状态里会留着上一个账号的痕迹（会话列表、历史记录）。
不清的话，下一轮跑完你看到界面上有内容，会以为成功了——
实际上那是上一轮的残留。

清理必须**按模式清**，不能逐个列举：本地状态目录带版本号，
写死几个路径迟早漏掉新出现的那个。

## 4. 代码在哪

主流程：`scripts/desktop/desktop-run.mjs`

| 阶段 | 关键符号 |
|---|---|
| 1 等信 | `findInvitationMail` + 每分钟心跳 |
| 2 建账号 | `driveToOtp` / `fillOtpAndSubmit` / `fillProfileAndSubmit` |
| 2.5 保登录态 | `detectPhoneStage` / `doPhone`（**不关浏览器**） |
| 3 起客户端 | `startDesktop` / `handshakeDesktop` |
| 4 走 OAuth | 阶段 4 的 while 循环（三个分支都在里面） |
| 5 确认成立 | `makeChallenge` / `classifyTurn` → [02 判据层](02-判据层.md) |

相关模块：

- `server/automationBrowser.js` —— 各个屏的识别与填写
- `server/desktopJudge.js` —— 所有判据（[02](02-判据层.md)）
- `server/automationMatch.js` —— 从信里认出邀请链接和验证码

**总预算**由 `WINDOW_BUDGET_MS` 控制，从信到达（`W0`）开始计时。
日志每行都带 `[+总耗时 窗口窗口内耗时]`，排查时先看这两个数字对不对得上。

**几个可覆盖的环境变量**（默认值都落在仓库内，不依赖特定部署布局）：

```
CODEX_SHOTS_DIR   出事时截图往哪写，默认 data/shots/
CODEX_URL_FILE    假 xdg-open 把 URL 写在哪，默认系统临时目录
CODEX_CDP_URL     客户端调试端口，默认 http://127.0.0.1:9333
```

> ⚠️ `CODEX_URL_FILE` 必须和你装的那个假 `xdg-open` 写入的路径**完全一致**。
> 两边不一致的表现是「一直等不到 OAuth 链接」，而真正的原因一条日志都不会说。
