# 06 · 双机反向拉取

> 执行器一个入站端口都不开。

## 1. 一句话

售卖站和执行器不在同一台机器上：一台对外，一台跑浏览器和桌面客户端。

它们之间要传任务。方向定成**执行器主动去售卖站取活**，
而不是售卖站把任务推给执行器。

一个方向的差别，换来的是：**执行器不用开任何入站端口，也不用为它改防火墙。**

## 2. 为什么不能用显而易见的做法

显而易见的做法是让售卖站直接调执行器的接口，或者两边共用一个队列库。

两条都不成立：

### 共用队列库不成立

队列存在本地数据库里。两台机器各自 import 同一个模块，
结果是**各自建一个空库**——看起来代码一模一样，实际是两个互不相干的队列。

这种错很隐蔽：本地开发时两个进程在同一台机器上，共用同一个文件，一切正常；
一上双机就静默失效，而且不报错，只是"任务发出去了但对面永远收不到"。

### 反向推送要开端口

让售卖站去调执行器，意味着执行器得监听一个对外可达的端口。
那台机器上跑着浏览器和一个带调试端口的客户端进程——
**它是整套系统里最不该暴露在公网上的一台。**

而且还得配防火墙、配证书、给它一个域名或固定 IP。为了传几个任务，
把攻击面扩大一整台机器，不划算。

## 3. 踩过的坑

### 3.1 方向定对了，两个问题一起消失

改成执行器当 HTTPS 客户端之后：

- 队列只有一份，在售卖站那边，**不存在"两个空库"的问题**
- 执行器只出不进，**零入站端口**
- 执行器换机器、换 IP、跑在 NAT 后面，都不用改任何配置

代价是执行器要轮询。对这个场景完全可接受——
任务本来就是分钟级的，空闲时几秒问一次没有任何压力。

> 一般规矩：**在"谁主动"上做选择时，先看哪一边更不该被暴露。**
> 让暴露面小的那一边当客户端。

### 3.2 口令比对必须防时序攻击

执行器拿一个共享口令去取任务。比对这个口令**不能用普通的字符串相等**——
那种比较会在第一个不同的字符处返回，比较时间泄漏了前缀是否正确，
理论上可以被逐字符猜出来。

用恒定时间比较函数。这是几行的事，不做就是白送。

### 3.3 没配口令时，接口应该整个关掉

如果口令没配置，正确行为不是"跳过校验"，是**这几个接口根本不存在**。

「没配就不校验」是最经典的配置型漏洞：本地开发方便，
上线时忘了配，接口就对全世界敞开，而且没有任何报错提示你。

### 3.4 网站不可达要退避，否则日志没法看

执行器连不上售卖站时，如果按正常间隔重试，日志会被刷屏，
真正的原因（口令不对？域名错了？服务没起？）淹没在里面。

所以正常轮询和故障退避是两个间隔：空闲几秒一轮，出故障几十秒一轮。
**退避的主要作用不是省资源，是让日志还能读。**

### 3.5 启动时缺配置就直接退出

执行器启动时如果缺了站点地址或口令，**立刻退出并说清楚缺什么**，
不要带着空配置跑起来。

带空配置跑起来的表现是：进程活着、日志在刷、看起来一切正常，
而每一次取任务都失败。运维看到"服务是 active 的"就不会去查它。

```js
if (!SITE || !SECRET) {
  console.error('缺 INVITE_SITE_URL 或 INVITE_WORKER_SECRET，worker 不启动');
  process.exit(2);
}
```

## 4. 代码在哪

```
售卖站（持队列）                     执行器（HTTPS 客户端）
server/inviteRoutes.js      ←────    scripts/invite-worker.mjs
  POST /api/invite/worker/next        取一个任务
  POST /api/invite/worker/report      回报结果
```

| 端 | 文件 | 说明 |
|---|---|---|
| 售卖站 | `server/inviteRoutes.js` | 队列的唯一真源；口令用恒定时间比较；没配口令则接口整个关闭 |
| 执行器 | `scripts/invite-worker.mjs` | 单进程串行消费（[05 并发闸](05-并发闸.md)），启动即校验配置 |

执行器需要的环境变量：

```
INVITE_SITE_URL          售卖站地址
INVITE_WORKER_SECRET     与售卖站 .env 里同名变量一致
INVITE_WORKER_TICK_MS    空闲轮询间隔，默认 5000
INVITE_WORKER_BACKOFF_MS 故障退避间隔，默认 30000
```

买家侧的三个接口在同一个文件里：

```
POST /api/invite/claim    验卡 → 分配（幂等，刷新不会多吃一份）
POST /api/invite/sent     买家确认 → 推进队列
GET  /api/invite/status   查进度
```

> `status` 对失败一律只回一句「失败，请联系客服」，**不把技术原因透出去**。
> 具体是 OAuth 超时还是接码没到，对买家没有任何可操作性，
> 只会变成"你们系统有问题"的争执。技术细节留在服务端日志里。

**单机部署**同样成立：把执行器和售卖站放同一台机器，
`INVITE_SITE_URL` 指向 `http://127.0.0.1:<端口>` 即可。
架构不变，只是两个进程住在一起。
