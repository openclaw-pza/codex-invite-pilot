# 10 · 支付与验签

> 接错了不会报错，只会静默全失败。

## 1. 一句话

支付这块只做两件事：**生成付款链接**，和**验证异步通知的签名**。

第二件是全系统唯一一处「验错了就有人不花钱拿到东西」的地方，
所以这个文件里每一条校验都对着一个具体的白嫖路径。

## 2. 为什么不能用显而易见的做法

### 显而易见做法之一：装官方 SDK

官方 SDK 会拉一长串传递依赖，而我们真正用到的就是
「参数排序拼串 → 签名 / 验签 → 拼一个链接」这点东西。

自己写清楚比包一层更好排错，也少一块供应链面。
**这个判断不通用**——如果用到的是 SDK 的十几个能力，那当然该用 SDK。
这里用到的是三个，而且都是标准密码学操作。

### 显而易见做法之二：验签就是"比对一下签名"

真正的坑不在比对，在**拼待签名串**。这一步有三个容易错的地方，
而且三个错法**全都不报错**，只表现为"验签一直失败"或者更糟——"验签一直通过"。

## 3. 踩过的坑

### 3.1 待签名串必须用未编码的原值

拼串时如果用了 URL 编码后的值，签出来的串对不上——
因为对方是拿**解码后的原值**算的。

表现是"验签一直失败，但看不出哪里错"。你会去检查密钥、检查算法、检查字符集，
而问题在一个你根本不会怀疑的地方。

### 3.2 公钥私钥搞反了，两个方向一起坏

有两把密钥：

- **我们自己的应用私钥** —— 用来给发出去的请求签名
- **支付平台的公钥** —— 用来验证收到的通知

搞反了会同时坏两件事：签名发不出去，验签全不过。
而报错信息**看不出是哪一头的问题**，因为两边的失败长得一样。

配置注释里必须写清楚哪个是哪个。这不是啰嗦，这是这个坑唯一的防线。

### 3.3 密钥格式：有没有头尾都要收

支付平台后台给的密钥常常是**没有 PEM 头尾的一长串 base64**，
而标准库只认带头尾的完整格式。

直接塞进去会报一个关于格式的错，而配置的人看着后台复制过来的那一大串，
完全不知道还要自己加东西。

做法是两种格式都收，内部统一补齐。

### 3.4 异步通知的响应必须是纯文本，多一个字符都不行

支付平台对通知响应有个硬要求：**只输出 `success` 这七个字符**。

回 JSON 会怎样？哪怕内容就是 `"success"`（带引号），它也判定为失败，
然后按 4 分钟 / 10 分钟 / 1 小时 / 2 小时 / 6 小时 / 15 小时的节奏
**一直重推 25 小时**。

而你这边看起来一切正常——通知收到了、订单处理了、日志里没有错误。
只有对方的重推日志知道你没回对。

所以有一个专门的纯文本响应函数，就是为这一条存在的。

### 3.5 通知的请求体不是 JSON

支付平台的异步通知是表单编码，不是 JSON。

而同一个服务上，另一个回调（订单系统的）**声明自己是表单编码，实际发的是 JSON**。
照声明解析的结果是：整段 JSON 变成一个字段名、值是空串，
于是所有字段读出来都是 undefined，那道"缺订单号就拒发"的闸把每一单都挡了，
整条商品线静默停发。

处理方式是**按声明分流之外再加一条判据**：正文本身长得像 JSON 就按 JSON 解。
判据卡得很死（首字符是 `{` 或 `[`，且整段能解析通过），
真表单不可能同时满足这两条，所以标准的支付通知不受影响。

> 一般规矩：**外部系统声明的 Content-Type 不可信。**
> 但也别一刀切地猜——加一条判据严格的兜底，比"先试 A 再试 B"安全，
> 后者会把恰好像 A 的 B 解析错，而且错得很难查。

## 4. 代码在哪

`server/alipay.js`（161 行）

| 函数 | 作用 |
|---|---|
| `toPem(key, label)` | 补齐密钥格式（§3.3） |
| `buildSignContent(params)` | 拼待签名串：字典序、跳过空值和签名字段本身、**用原值**（§3.1） |
| `buildPayUrl(...)` | 生成付款链接 |
| `verifyNotify(...)` | 验证异步通知签名 |

配置：

```
ALIPAY_APP_ID
ALIPAY_APP_PRIVATE_KEY   ← 我们自己的应用私钥
ALIPAY_PUBLIC_KEY        ← 支付平台的公钥（别和上面搞反，§3.2）
ALIPAY_GATEWAY
ALIPAY_NOTIFY_URL        ← ⚠️ 必须是你自己的域名
ALIPAY_RETURN_URL
```

> ⚠️ `ALIPAY_NOTIFY_URL` 照抄别人的值 = 你的支付回调打到别人服务器上。
> 而这个错**不会报错**，只表现成"买家付了钱但订单一直不到账"。
> `.env.example` 里这两项刻意留空。

**配到一半比不配更糟**：这几项不配齐时，系统会走「扫码 + 备注 + 人工核对」那条路，
功能完全不受影响。而配了一半的后果是买家点了付款拿到一个空链接。
所以判断是"全配齐才启用"，不是"配了就用"。

测试在 `test/alipay.test.js` 和 `test/alipay-notify.test.js`——
**上面每一条坑都有对应用例**。改这个文件之前先跑它们。
