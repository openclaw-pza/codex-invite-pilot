## 1. 一句话

这条链路依赖几样**整机只有一份**的东西：一个固定的调试端口、
一个固定路径的凭据文件、一个客户端进程。

两轮同时跑的时候，它们不是"变慢"，是**互相把对方毁掉**：
第二个实例清掉第一个的凭据、抢走端口，然后两轮一起死，
两份不可再生的库存一起烧。

## 2. 为什么不能用显而易见的做法

显而易见的做法是加个内存里的标志位：正在跑就拒绝新任务。

它挡不住三种情况，而这三种在真实运维里全都会发生：

1. **同一台机器上的另一个进程。** 运维手工跑一次排查，和后台服务撞上——
   两个进程各有各的内存，标志位互相看不见。
2. **进程重启。** 标志位随进程消失，上一轮留下的客户端进程还活着。
3. **分配层的竞态。** 两次拉取任务之间，同一份库存被发给了两个消费者——
   这时候还没到"开始跑"那一步，标志位根本没机会拦。

一道锁挡不住三种情况。所以是四道，每一道拦一层。

## 3. 踩过的坑

### 3.1 四道闸，分别拦什么

| # | 闸 | 拦哪一层 |
|---|---|---|
| 1 | **单进程串行消费** | 并发从根上不存在——队列消费者只有一个，顺序取任务 |
| 2 | **整机 pid 锁** | 后台服务和手工运行撞车 |
| 3 | **先占位再交付** | 两次拉取之间把同一份库存发给两个消费者 |
| 4 | **数据库唯一索引** | 前三道全漏掉时的最后一层 |

这不是过度设计。**第 1 道是最有效的**——它让并发问题在结构上不成立。
后三道是承认"结构总有被绕过的一天"之后的兜底。

### 3.2 锁里必须记 pid，否则会把自己永久锁死

第一版的锁是「文件存在就算被占」。

问题在于：进程被强杀、机器断电、容器重启——这些情况下文件还在，
而占用它的进程早没了。于是**下次启动直接被自己上一次留下的锁挡住**，
而且永远不会自己恢复。运维得先知道有这么个文件，才能删掉它。

改法是锁里写进程号，检查时先看那个进程还在不在。
进程没了就是失效锁，直接覆盖。

```js
export function lockHolder() {
  let prev;
  try { prev = JSON.parse(readFileSync(RUN_LOCK_PATH, 'utf8')); } catch { return null; }
  try { process.kill(prev.pid, 0); } catch { return null; }   // 进程已死 = 失效锁
  return prev;
}
```

> `process.kill(pid, 0)` 不发信号，只探测进程存不存在。这是标准做法。

### 3.3 抢不到锁应该返回，不是抛异常

`acquireRunLock` 抢不到时返回占用者，不抛错。

原因是**两个调用方对"抢不到"的处理完全不同**：

- 手工运行的命令行：直接退出，告诉人"现在有一轮在跑"
- 后台队列消费者：退避一会儿再试，不能退出

如果这里抛异常，两边都得写 try/catch，而其中一边其实只是想读一个状态。
**把"是否失败"和"怎么处理失败"分开，是这类基础设施该有的形状。**

### 3.4 先置状态再交出去

拉取任务这一步，正确顺序是：

```
在数据库里把这份库存标成"进行中"  →  然后才把它返回给消费者
```

反过来（先返回、消费者拿到后自己标记）中间有一个窗口，
第二个消费者可以在这个窗口里领到同一份。

窗口很短——但不可再生的库存不接受"概率很低"。

### 3.5 两处共用同一把锁，别各写一份

需要这把锁的有两处：后台队列消费者，和手工运行的命令行。

它们如果各写一套锁逻辑，结果一定是**只有一边生效**——
两边的锁文件路径、判定方式、清理时机迟早会漂移，而且漂移是静默的。

所以抽成一个模块，两边 import 同一份。

> 这是那条通用规矩的又一个实例：**一个定义只能有一处。**
> 同一件事在两个地方各写一份判断，它们必然会漂移。

## 4. 代码在哪

| 闸 | 位置 |
|---|---|
| 单进程串行消费 | `scripts/invite-worker.mjs`（整个文件的设计前提） |
| 整机 pid 锁 | `server/runLock.js`（44 行） |
| 先占位再交付 | `server/inviteRoutes.js` 的 worker 拉取接口 |
| 数据库唯一索引 | `server/accountPool.js` 建表处 |

`runLock.js` 的三个导出：

```js
lockHolder()            // 谁占着？没人占或占用者已死 → null
acquireRunLock(label)   // 抢到 → null；没抢到 → 占用者信息
releaseRunLock()        // 释放
```

锁文件路径可以用 `RUN_LOCK_PATH` 覆盖，默认在仓库的 `data/run.lock`。

**异常中断后的清场**（客户端或浏览器进程残留时）：

```bash
pkill -9 -f "[d]esktop-run"
pkill -9 -f "[c]hromium"
rm -f data/run.lock
```

> 方括号写法不是装饰：`pkill -f` 会匹配到**它自己的命令行**，
> 不这么写的话这条命令会先把自己杀掉。
