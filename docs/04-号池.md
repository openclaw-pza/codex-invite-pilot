# 04 · 号池 · 不可再生库存

> 有一种库存，用一次就没了、补不回来。

## 1. 一句话

普通库存是**可数的**：卖掉一件减一件，补货就加回来。

有一类库存不是：一个只能被邀请一次的账号、一次性的额度、限量券。
它们的共同点是——**用错一次就永久少一份，花钱也买不回来**。

这类库存不能用「减库存」那套模型管，得用状态机。

## 2. 为什么不能用显而易见的做法

显而易见的做法是给库存表加个 `used` 字段：分配的时候标记，用完确认。

它漏掉的是**分配和使用之间那段时间**。而对不可再生库存来说，这段时间里能出的事最多：

- 买家领了但半天不回来
- 领了之后流程失败，要不要退回去
- 系统重启了，那些"正在用"的怎么办
- 两个消费者同时领到同一份

更要命的是第五种，也是这个项目最贵的一条教训：

> **分配这个动作本身，就可能把库存毁掉。**

## 3. 踩过的坑

### 3.1 「分配」绝不能碰真实资源

第一版实现里，「把一个账号分配给买家」这一步顺手做了初始化——登录一下，
确认它是好的。听起来很负责任。

实际后果：那个平台在**首次登录时**会强制要求绑定一个恢复邮箱，
而我们绑的是一个约十分钟就失效的临时地址。

于是：**邀请还没来，恢复邮箱先死了。** 这个账号从此没有找回途径，
等于白废一份不可再生的库存——而它甚至还没被真正使用过。

**所以规矩是：分配只在数据库里做一次指派，一个字节都不碰真实资源。**
不登录、不绑定、不取令牌，只把地址发出去。

真正开始用它，是买家回来点确认之后的事。

> 这条规矩可以直接迁移：**"检查一下它是不是好的"这个动作，
> 对某些资源来说本身就是消费。** 加健康检查之前先问一句，
> 这个检查会不会改变被检查对象的状态。

### 3.2 想做入库体检？那得挑不留痕的方式做

上一条说了「分配时不能碰」，但**入库时**是可以也应该体检的——
坏凭据不体检，只会在买家的名额已经烧掉之后才暴露。

关键是体检的方式要选对：

- ✅ 换一次令牌**并真读一次数据** —— 不改变账号状态
- ❌ 用密码登录一次 —— 触发首次登录的那套强制流程

而且**只拿到令牌不算数**：有的令牌换得到，但授权范围里没有读取权限，
实际用起来一样是废的。**接口返回成功 ≠ 事情能办成。**

### 3.3 陈旧任务回收：读不出时间戳就别动它

有些任务会永远停在"正在进行"——进程崩了、机器重启了。
所以需要一个回收器：超过一定时间还在进行中的，放回队列。

第一版写成了「时间戳读不出来 → 当作已超时 → 放回队列」。

这是个 fail-open，后果很具体：**把正在跑的那一轮也放回了队列**，
第二个消费者领走，两轮同时操作同一份不可再生库存，一起烧掉。

改法是反过来：**读不出时间戳就不动它。** 宁可让一个真卡住的任务多占一会儿，
也不能把活着的任务抢走。

### 3.4 应用层的检查会有 bug，数据库约束不会

「一张卡只能挂一个活跃资源」这条不变量，代码里当然有检查。
但代码检查在并发下有窗口期，而且以后每加一条新路径都可能绕过它。

所以同一条规则**在数据库层再写一遍**：一个唯一索引。

应用层的检查负责给出友好报错，数据库约束负责**保证它真的不会发生**。
两者不是重复，是分工。

### 3.5 并发配置比想象中重要

数据库默认是「撞锁立刻抛，一毫秒都不等」，而且读也挡写。
审计实测：6 个进程并发时 **51% 的请求直接抛「database is locked」**——
运维随手敲一句查状态的命令，就能把分配流程打挂。

改成 WAL 模式 + 设置忙等待超时之后这个问题消失。
**这类默认值不是性能调优，是能不能用的问题。**

## 4. 代码在哪

`server/accountPool.js`（302 行）+ `scripts/pool.mjs`（命令行）

### 状态机

```
available ──claim──> assigned ──confirm──> ready ──run──> running
                        ^                     |               |
                        └──── unconfirm ──────┘   finish ─────┴──> done / failed
                                                  reset ──────────> ready

     任意状态 ──markDead──> dead（永久移出可分配集合）
```

| 状态 | 含义 |
|---|---|
| `available` | 还没分配，可以领 |
| `assigned` | 已分配，**但一个字节都没碰过** |
| `ready` | 买家确认了，排队等执行 |
| `running` | 正在执行 |
| `done` / `failed` | 跑完 / 失败 |
| `dead` | 资源本身废了，永久移出 |

### 关键函数

| 函数 | 注意什么 |
|---|---|
| `claimAccount(ref)` | **只写数据库**。这是 §3.1 那条硬约束的实现处 |
| `confirmInvite` / `unconfirmInvite` | 推进 / 退回队列 |
| `markRunning` / `markFinished` | 状态流转 |
| `resetToReady` | 失败重跑。**能重跑就重跑**——换一份等于白扔一份 |
| `markDead` | 只在确认资源本身废了时用 |
| `reclaimStaleRunning` | §3.3，读不出时间戳就不动 |

### 命令行

```bash
node scripts/pool.mjs add 账号文件         # 入库
node scripts/pool.mjs verify --mark-dead   # 入库体检（§3.2）
node scripts/pool.mjs status               # 看各状态数量
node scripts/pool.mjs release  --address x # assigned → 退回
node scripts/pool.mjs unconfirm --address x # ready → 退回
node scripts/pool.mjs reset --address x --force  # failed/done → 重跑
```

发货行的解析在 `server/accountLine.js`——它也是一个判据，
坑记在 [02 判据层 §3.4](02-判据层.md#34-另外两个判据两种不同的贵法)。
