# 02 · 判据层

> 机器怎么知道自己这一步真的做成了。

## 1. 一句话

自动化跑起来之后，代码干了什么和它**以为**自己干了什么，是两件事。

有人在旁边看着的时候，这两件事的差距会被人眼当场抹平——屏幕上明明没反应，你自己就知道没成。
一旦没人看着，**「以为」就是全部**：机器认为成了，它就往下走；后面所有步骤都建立在这个判断上，
错了也没人喊停。

判据层就是专门装「怎么判断这一步成了」的地方。这个项目里，它是所有代码中最贵的一部分——
不是因为难写，是因为**写错的代价是不可逆的**。

---

## 2. 为什么不能用显而易见的做法

显而易见的做法是：**看界面上出现了什么字**。

发了一条消息，等页面上多出一段文字，多出来了就是回复到了。听起来无懈可击，
真实的自动化教程也基本都这么教。

它错在一个地方：**界面文本是对方的东西，不是你的。**

它没有契约、不承诺稳定、随版本漂移，而且会冒出各种你没见过的新内容——
会话标题、加载中的状态字、无障碍朗读标签、报错弹条、更新提示。
你的判据不是在读「回复」，是在读「一块你控制不了的画布上今天恰好长什么样」。

更麻烦的是它**坏得很安静**：

- 不报错
- 不留日志
- 不会有任何一行提示你「判据失效了」

它只是从某一天起，开始一直判错。而你发现的方式，通常是发现资源莫名其妙少了一批。

## 3. 踩过的坑

### 3.1 同一个判据，一天之内错了四次

2026-08-26，判断「发出去的消息到底有没有被回答」这一件事，判据改了四版，
**每一版都白烧一个不可再生的名额**。四次的根因各不相同：

| 版本 | 做法 | 怎么死的 |
|---|---|---|
| v1 | 新增文本长度超过 40 字符就算收到回复 | 真回复是 `You're welcome.`——15 个字符。**漏报** |
| v2 | 数「助手气泡」的个数 | 那是**网页版**的结构，桌面客户端里根本匹配不到。检测整个瞎掉 |
| v3 | 按消息长度增量算 | 界面是**虚拟列表**：旧消息滚出视区就从结构里移除。对话越长，净增长越小，越靠后的消息越吃亏 |
| v4 | 比对文本行的集合差 | 命中的是 `You said:`——那是**自己发出的消息**的无障碍标签。也就是说，回复永远不来也会报成功 |

v4 是最贵的一次。前三次是漏报（明明成了却判没成，最多重跑一次），
**v4 是误报**——判据说成了，实际什么也没发生，而后续所有步骤都当它成了。

> **误报比漏报贵得多。** 漏报浪费一次重试，误报污染之后的全部状态。
> 判据在拿不准的时候，应该往「没成」的方向倒。

### 3.2 第五版：不再依赖界面长什么样

四次翻车的共同点不是「阈值调得不对」，是**判据依赖了不可控、无契约、随版本漂移的界面文本**。
在措辞上继续调，调多少版都会有第五次。

换个思路：**让回复里必须出现一个「只有真正回答的人才产生得出来」的串。**

做法是发一道算术题，比如「611 加 322 等于多少」，然后在界面上找 `933`。

关键在于**答案不能出现在题面里**。这样一来：

- 消息回显 → 造不出 933
- 无障碍标签 → 造不出 933
- 会话标题 → 造不出 933
- 加载状态字 → 造不出 933

只有真的算了这道题的一方，才能让 933 出现在屏幕上。

这不是更聪明的字符串匹配，是**换了个东西去判**：从「界面看起来对不对」，
换成「有没有发生一件只有成功时才可能发生的事」。

### 3.3 读不到 ≠ 成功

第三种结果叫 `unverifiable`——**界面读不到**。

这一条单独拎出来说，是因为它极其容易被写成 bug：读取界面的代码包了 try/catch，
出错时返回空字符串，然后判据拿空字符串去匹配，匹配不到「失败」的特征，
于是**判成了成功**。

这叫 fail-open。它的特征是：**故障越严重，越判成功**。界面彻底崩了、进程死了、
连接断了——这些情况下什么都读不到，而 fail-open 的判据会在这些时刻给出最乐观的结论。

所以结果必须是四种，不是两种：

```
confirmed     看到了只有真回答者才产生得出的证据
fatal         界面明确在报错或限流，继续做没有意义
unverifiable  读不到。既不是成功也不是失败，是「不知道」
pending       还没等到，继续等
```

「不知道」必须能被表达出来。一个只有「成功/失败」两种输出的判据，
一定会把「不知道」塞进其中一边——而塞进哪边都是错的。

### 3.4 另外两个判据，两种不同的贵法

**认卖家发来的账号行**（`accountLine.js`，39 行）

发货格式是 `邮箱----密码----client_id----令牌`。老写法用
`split(/----|[\s,|]+/)` 切，把空格、竖线、逗号也当分隔符。
后果：**密码里带空格就被静默砍半**——审计实测 `a@o.com----Pw 123` 解析出来的密码是 `Pw`。

而这个错的表现是「登录失败」，看起来像**号本身是坏的**，于是好号被标记成废号扔掉。
判据错了，代价记在了别人头上。

改法是**按形状认，不按位置认**：长得像 UUID 的是 client_id，长度 60 以上的是令牌。
卖家的字段顺序不保证，按位置写死迟早把令牌存进 client_id——而那种错同样是静默的。

**判卖家给的令牌是不是活的**（`outlookToken.js`）

这里的教训是**失败分类的代价不对称**：

- 把**瞬时故障**判成「号已死」→ 一次网络抖动换掉一个好号
- 把**已死的号**判成瞬时故障 → 只是多等一轮，下次再查

两边代价差着数量级，所以判据必须偏保守：**只有对方明确说这个凭据不能用了，才算死。**
429、5xx、没见过的错误码，一律当瞬时故障。

还有一条：**校验必须真的读一次数据**。只拿到令牌不算数——
有的令牌换得到，但授权范围里没有读取权限，实际用起来一样是废的。
「接口返回 200」和「事情办成了」是两回事。

## 4. 四条规矩

前面每一条都是损失换来的，写在这里当检查表：

1. **判据抽成纯函数，用真实抓到的原文钉测试。**
   埋在几百行流程里的判据，一行测试都写不了。抽出来之后，
   每一次翻车的真实界面文本都能变成一条回归用例——`desktop-judge.test.js` 的 17 项就是这么来的。

2. **判据落在产物上，不落在动作上。**
   不问「这个按钮点成功了吗」，问「页面变了吗 / 文件写了吗 / 状态改了吗」。
   点击这个动作永远会「成功」，它只代表事件派发出去了。

3. **读不到 ≠ 成功。** 见 §3.3。

4. **失败分类偏保守。** 见 §3.4。只有对方明确说不可用才判死。

还有一条是从部署脚本上学到的、但对判据同样成立：
**「传上去了」不等于「生效了」**（见 [11 部署校验](11-部署校验.md)）。

## 5. 代码在哪

| 文件 | 判什么 | 测试 |
|---|---|---|
| `server/desktopJudge.js` | 客户端在哪一屏、消息有没有被真回答 | `test/desktop-judge.test.js`（17 项） |
| `server/outlookToken.js` | 卖家给的令牌能不能用 | `test/outlook-token.test.js`（8 项） |
| `server/accountLine.js` | 发货行怎么切 | `test/account-line.test.js`（8 项） |

关键函数：

```js
// server/desktopJudge.js
makeChallenge(rand)          // 造一道答案不在题面里的算术题
classifyTurn(text, expect)   // → confirmed | fatal | unverifiable | pending
desktopTextLoggedIn(text)    // 必须有正向证据，不能靠"不是登录页就算登录"
```

`desktopTextLoggedIn` 里那句「必须有正向证据」值得单独看一眼：
纯反向判据（「不是登录页 → 那就是登录了」）会把等待屏、错误页、加载中**全部**判成已登录。
这又是一个 fail-open——而它的后果是关掉那个唯一持有登录会话的浏览器。

## 想自己动手改

判据类改动**必须带真实抓到的原文作为测试用例**，不接受只有 mock 的测试。

原因就是这一篇讲的全部内容：判据的 bug 不在逻辑里，在**你以为界面长什么样**和
**界面实际长什么样**之间。用自己编的字符串写测试，等于把同一个误解写两遍。
